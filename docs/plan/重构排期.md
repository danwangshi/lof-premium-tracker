### 1.5 舍入面（迁移风险量化）

| 项 | 实测 |
|---|---|
| `round()` 调用（后端，不含测试） | **68 处，涉及 12 个文件** |
| 精度分布 | `round(x,2)` **32 处**、`round(x,4)` **14 处**、`round(x,1)` 1 处、`round(x,0)` 1 处 |
| 最集中文件 | `profit_service.py` 20、`est_nav.py` 11、`fund_service.py` 10、`calculator.py` 9 |

**四种舍入语义实测对比**（同一批输入，结果互不相同）：

| 输入 | Python `round(x)` | JS `Math.round(x)` | Python `round(x,2)` | JS `toFixed(2)` | JS `Math.round(x*100)/100` |
|---|---|---|---|---|---|
| 2.5 | **2** | **3** | — | — | — |
| 0.5 | **0** | **1** | — | — | — |
| 0.125 | — | — | **0.12** | **0.13** | 0.13 |
| 2.675 | — | — | **2.67** | 2.67 | **2.68** |

即：**Python 是银行家舍入（round-half-to-even）、PostgreSQL `round()` 是四舍五入
（half-away-from-zero）、JS 的三种写法互相也不一致**。差异正好落在用户直接看的位数上
（溢价率 2 位、估算净值 4 位）。详见约束 **C7**、风险 **K9**、任务 **R1.8.2**。

## 2. 硬约束（这些决定了方案不能怎么选）

| # | 约束 | 后果 |
|---|---|---|
| C1 | **内存 1673 MB、无 swap，PostgreSQL 与 Redis 同机** | **不能靠调大 `maxmemory` 解决缓存被淘汰**。Redis 峰值已 515.97M/512M，再调大会把 PG 推到 OOM。唯一出路是**缩小键**。 |
| C2 | 磁盘 47%，充裕 | 存储重构的动机是**内存与查询效率**，不是磁盘 |
| C3 | **无 CI、无类型检查、前端零测试** | 在动 **598h** 级重构之前必须先建安全网，否则重构本身无法验证 |
| C4 | 后端测试有 15 个既有失败 | 不修就无法区分「我改坏了」和「本来就红」——本会话已为此付出过一次 HEAD worktree 对比的成本 |
| C5 | 金融数据的正确性是产品底线 | 任何重构都不得引入静默错误。本项目已发生 ≥3 次静默失败（certbot 续期、切片入库、`cache_set` 吞异常） |
| C6 | `statement_timeout = 5s` | 重构期间的批量迁移/统计查询会被静默掐断，迁移脚本必须显式关超时并分片 |

## 3. 需求与依赖链（含为什么是这个顺序）

### 3.1 五项需求的相互关系

```
要求 5（资产清单：股票/指数/债券/期货/货币/基金）── 数据模型定稿 ──┐
                                                                    ├──→ 要求 4（存储重构）──→ 要求 1（全栈 TS，含要求 2 验收）──→ 要求 3（多端）
要求 2（层级拆分）──────────────────────────────────────────────────┘
```

### 3.2 三条必须遵守的顺序（排错了就白做一遍）

**① 要求 2 不单独排期 —— 它是要求 1 的验收标准。**

TS 重写时天然就要拆文件。分两轮做就是**同一批文件改两遍**。因此要求 2 作为要求 1 的
**硬性验收条件**（见 §7.4），不单独给工时。

**② 要求 4 必须排在要求 1 之前。**

存储是**数据契约**，代码是消费者。先迁代码，ORM/查询层写完还要再改一遍数据结构；
反过来只需改一次。**全栈迁移让这条更重要** —— 后端换语言的同时换 schema 是双重变量，
出了问题无法定位是哪一边造成的。

**③ 要求 5 的数据模型必须排在要求 4 之前定稿。**

`fund_asset_map` 现假设「持仓是资产」。用户已确认要**扩展关系表**并补全
债券/期货/货币等类别（§4）。不定稿就重构存储，拆分/分区方案会白做。

#### 行为契约清单（R1.8.1 的必做产出）

> 下面这些是**代码里的隐性行为**。Python 侧没有任何机制强制它们，但**用户可见**。
> 不显式列出就会在重写中丢失。**这是这 180h 里最容易出事的部分。**

- `_est_is_meaningful`：零输入估算（两个贡献都是 0 且 `est_nav == 基准净值`）**不展示**
- `_est_nav_data_to_records`：当日净值公布后的切片**不再挂到该 trade_date**（判据只比日期，不比数值）
- `nav_sync` 的「归位」语义：取 `nav_date <= 该交易日` 的最新净值；`nav_date` 如实记录、**不做日期伪装**
- `merge_nav_map` 的**单调性**：不用更旧的 `nav_date` 覆盖更新的
- `safe_set_realtime` 的部分数据防护阈值
- `cache_set` / `cache_get` 的**降级语义**（缓存坏了不能把业务请求带崩）
- `beijing_now` / `beijing_today_date` 与 DB 侧的时区交互
- `statement_timeout = 5s` 下的查询预算（**每条查询都必须落在预算内**）
- 分页常量：`PAGE_SIZE_DEFAULT 600` / `ETF_PAGE_SIZE 2400`
- `fund_snapshot` 物化视图的**版本化重建**与列加宽的顺序约束
- `_est_time_label`：估算时间必须是**后端真实生成时刻**，不能用浏览器当前时间
- 各运维脚本的口径（`purge_non_exchange` / `sync_fund_universe` / `repair_nav_alignment`）
